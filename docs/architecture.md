# Архитектура gwu

## Структура кода

Один Go-модуль в `src`, одна точка входа `src/cmd/gwu/main.go`.

| Каталог | Назначение |
| --- | --- |
| `src/internal/gwucli` | Сборка дерева Cobra-команд, встроенная версия |
| `src/modules/wireguard` | Модели, валидация, metadata, конфиги и вызовы wg/systemctl |
| `src/modules/qos` | Общий канал, Netlink, конфигурация, ownership и блокировка |
| `src/internal/layout` | Пути модулей |
| `src/internal/atomicfile` | Замена одного файла через временный файл и rename |
| `src/internal/command` | Интерфейс системных команд, подменяемый в тестах |
| `src/internal/buildtests` | AST-проверка структуры CLI-команд |
| `debian/common`, `debian/gwu` | Общие правила и metadata Debian-пакета |

Каждая прикладная CLI-команда находится в отдельном
`command/<имя>/<подкоманда>/root.go` и предоставляет `NewCommand`.
Родитель регистрирует детей, команда владеет flags и handler.
Domain-код не импортирует Cobra, WireGuard и QoS не импортируют друг друга.
Деревья команд не имеют общего изменяемого состояния flags.

## Данные

```text
/etc/wireguard/gwu/
├── wireguard/
│   ├── <interface>.json
│   ├── clients/<user>.json
│   ├── configs/<user>.conf
│   ├── templates/*.tmpl
│   └── generated/
│       ├── <interface>.conf
│       └── gateway.conf
└── qos/
    ├── channel.json
    ├── templates/*.tmpl
    ├── generated/qos.service
    └── state/
```

Рабочий конфиг wg-quick — `/etc/wireguard/<interface>.conf`.
Первоначальная настройка записывает IPv4 forwarding в
`/etc/sysctl.d/90-gwu.conf`. Каталоги создаются с правами 0700,
metadata и клиентские конфиги — 0600. JSON содержит ключи; generated gateway
и systemd unit — 0644, внутри закрытых каталогов.

Пользовательские операции ожидают ровно один JSON сервера в
`wireguard/`. Наличие команды установки интерфейса с произвольным именем
не означает поддержки управления пользователями нескольких серверов одновременно.

## WireGuard

Серверные и клиентские модели сериализуются через encoding/json.
Шаблоны конфигов встроены через go:embed и копируются на диск при отсутствии.
Существующие локальные шаблоны обновление пакета не заменяет.

Операции add/remove/block/unblock меняют metadata, регенерируют конфиг и вызывают
restart соответствующего wg-quick unit. Клиентский конфиг создаётся при добавлении.
Между metadata, клиентским конфигом, серверным конфигом и restart нет общей
транзакции: после ошибки необходимо проверить фактическое состояние.

Установка сервера отказывается перезаписывать существующий активный конфиг.
`wireguard init` — первичная настройка, не механизм обновления.

NAT принадлежит отдельной nftables-таблице для интерфейса:
`gwu_nat_` + hex имени, например `gwu_nat_776730` для wg0.
PostUp использует exclusive create; PostDown удаляет свою таблицу.
Шаблон не настраивает filter/FORWARD или source routing rules.
Masquerade применяется ко всему трафику через выбранный внешний интерфейс,
без ограничения source-подсетью.

## QoS

Модуль управляет одним общим egress-каналом:
HTB root `1:` → class `1:fffe` с rate=ceil → FQ-CoDel `10:`.
Linux Netlink используется напрямую, shell-скрипт tc не генерируется.
Rate ограничен диапазоном от 8Kbit до 100Gbit и должен быть кратен 8bit.

При изменении rate обновляется принадлежащий модулю класс без удаления root.
State и flock защищают от параллельных операций и захвата чужой очереди.
Одинаковые handles без корректного ownership не разрешают изменение или удаление.

Состояние на диске не защищает от ручных изменений root. При незавершённом
создании либо несовпадении state и очередей требуется ручная диагностика.
Общей транзакции с сетью и гарантии fail-closed нет.

`qos init/render` только генерируют файлы. Systemd unit не устанавливается
автоматически. В шаблоне нет ExecStop: остановка или restart unit сами по себе
не удаляют root qdisc. Удаление выполняет явная команда `qos down`.

## Тесты

`make test` проверяет CLI, storage, шаблоны и QoS с подменёнными системными
вызовами/Netlink. `go vet ./...` запускают внутри `src`.

Linux integration tests включаются переменной `GWU_TEST_NET_ADMIN=1` и требуют
одноразового Docker-контейнера с собственным network namespace и CAP_NET_ADMIN.
Их нельзя включать на хосте, с host networking или с подключёнными рабочими
каталогами `/etc/wireguard`. Обычный запуск тестов пропускает эти сценарии.
